# Autonomous Multi-Agent System (AI Agency)

![Status](https://img.shields.io/badge/status-experimental-yellow)

Иерархическая мультиагентная система с менеджером-оркестратором, который 
декомпозирует глобальную задачу и делегирует шаги специализированным отделам. 
Каждый отдел - это отдельный LangGraph-граф со своим циклом исполнения и контроля качества.

## Архитектура

```
                    ┌─────────────────────┐
                    │   Manager (цикл)    │
                    │=====================│
                    │ thinker → delegator │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
        ┌──────────┐    ┌──────────┐     ┌──────────┐
        │ Developer│    │ Content  │     │ Analyst  │
        │==========│    │==========│     │==========│
        │ coder →  │    │research →│     │ worker → │
        │ tester → │    │writer →  │     │ QA →     │
        │ reviewer │    │typesetter│     │ saver    │
        └──────────┘    │ → editor │     └──────────┘
                        └──────────┘
```

**Manager** получает глобальную задачу, ведёт журнал выполненных шагов (`step_history`) 
и на каждой итерации решает: завершить работу или сформулировать следующий шаг для одного 
из трёх отделов. Защита от зацикливания - лимит в 15 итераций.

**Developer** - пишет и тестирует код, проходит ревью на соответствие ТЗ. Полезные решения 
могут быть сохранены как переиспользуемые инструменты в `tools/registry.json` - 
система способна **динамически расширять свой собственный набор инструментов**.

**Content** - собирает данные, пишет текст, верстает в LaTeX и компилирует PDF, 
с циклом доработки по замечаниям редактора.

**Analyst** - анализирует неструктурированные данные из памяти, приводит их к структурированному 
виду (JSON), проходит проверку QA.

## Общая память (Shared Memory)

Все агенты системы читают и пишут в единое JSON-хранилище (`memory.json`) 
через инструменты `memory_save` / `memory_load`. Чтобы не раздувать контекст 
LLM полным содержимым памяти, Manager получает только **индекс** - список 
ключей с их описаниями (`get_memory_index()`), а полные данные подгружаются 
отделами по необходимости через соответствующий инструмент.

Именно отсутствие верификации того, что записывается в эту память 
(см. "Известные проблемы"), - одна из главных причин нестабильной работы системы.

## Пример успешного запуска

Система самостоятельно придумала и выполнила мини-проект - сравнение погоды 
в нескольких городах мира с построением графиков (matplotlib) и версткой итогового 
PDF-отчёта через отдел Content. Пример результата: [`examples/weather_comparison_report.pdf`](examples/weather_comparison_report.pdf).

## Известные проблемы

Система работает нестабильно - успешное завершение задачи наблюдалось примерно 
в 10% запусков. Основные причины:

- **Галлюцинации на этапе веб-поиска.** Агенты часто получали из интернета 
  неточную или нерелевантную информацию и сохраняли её в память как достоверную, 
  без проверки. Например, в примере с погодой данные на графиках, вероятно, 
  не полностью соответствуют реальным - подтвердить точность не удалось.
  
- **Засорение памяти.** При попытке составить отчёт об истории Илона Маска система
  сохранила в память противоречивый и нерелевантный текст с разных страниц,
  после чего не смогла выстроить из него связный анализ - отчёт не содержал осмысленной информации.
  
- **Бесконечные циклы.** Из-за недопонимания между Manager и отделами (или 
  зацикленных исправлений кода в Developer) система иногда не продвигалась к цели 
  до истечения лимита итераций.

- **Неконтролируемое создание инструментов.** Developer иногда сохранял в реестр 
  бесполезные или дублирующиеся инструменты (например, узкоспециализированную 
  функцию `main`, пригодную ровно для одного случая), что засоряло `tools/registry.json` 
  и путало Manager при планировании следующих шагов.

## Выводы

Главный урок этого проекта - **автономность агентов без механизма верификации фактов 
и контроля состояния памяти быстро приводит к накоплению ошибок**: неточные данные 
на одном шаге становятся фактом для всех последующих шагов, и система не умеет 
усомниться в собственных же данных.

Что стоило бы добавить, если продолжать проект:
- отдельный шаг верификации/перепроверки фактов перед сохранением в память 
  (например, сверка данных из нескольких источников);
- структурированная схема памяти вместо произвольных ключ-значение записей, 
  чтобы Analyst/Content не работали с "грязными" данными;
- периодическая чистка `tools/registry.json` от неиспользуемых/дублирующихся инструментов;
- более строгая типизация шагов делегирования между Manager и отделами, 
  чтобы снизить количество ошибок маршрутизации.

## Технологии

- Python, LangGraph, LangChain (ChatOpenAI)
- LaTeX (компиляция отчётов в PDF)
- Web search / scraping инструменты

## Установка

```bash
git clone https://github.com/gmdEGXYZ/ai-agency-mas.git
cd ai-agency-mas
pip install -r requirements.txt
cp .env.example .env
# заполните .env своим API-ключом
```

## Запуск

Глобальная задача задаётся прямо в `main.py` в переменной `global_task` 
(интерфейс ввода задачи не реализован):

```bash
python main.py
```
